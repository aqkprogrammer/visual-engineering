<Definition>

A **Docker image** is a read-only package of everything an application needs to run — files, libraries, settings — built as a stack of **layers**, one for each filesystem change in its Dockerfile. A **container** is a running instance of an image with a thin writable layer on top.

</Definition>

## The problem it solves

"It works on my machine" happens because software depends on far more than its own code: a language runtime of a particular version, system libraries, configuration files, environment variables. Every machine has a slightly different mix.

An image captures that whole environment once, in a form that can be copied anywhere and started the same way every time. Building it as **layers** makes this efficient: layers that haven't changed are reused from cache when building, skipped when pushing and pulling, and shared between images and containers on the same machine.

## An everyday analogy

<Analogy>

Think of a stack of transparent sheets on an overhead projector. The bottom sheet has the operating system, the next adds the runtime, the next your dependencies, the top one your code. Looking down through the stack you see one complete picture. To change your code, you only redraw the top sheet.

</Analogy>

Where the analogy breaks down: with Docker's build cache, redrawing a sheet also forces every sheet *above* it to be redrawn, even if their content would be identical. That one rule is why the order of instructions in a Dockerfile matters so much.

## Step by step: building an image

<Steps>

1. **The build context.** `docker build .` sends the files in the directory (minus anything listed in `.dockerignore`) to the builder.
2. **One instruction at a time.** For each instruction the builder computes a cache key from the parent layer, the instruction text and — for `COPY` and `ADD` — the files being copied.
3. **Cache hit or miss.** If a layer with that key already exists, it is reused instantly. If not, the instruction runs and produces a new layer.
4. **Everything after a miss rebuilds.** Once one layer changes, every later layer has a different parent, so none of them can come from cache.
5. **The result** is a list of layers plus a configuration (environment variables, the default command, exposed ports). Instructions like `CMD` change only that configuration and add no filesystem layer.

</Steps>

## Example: order instructions from least to most frequently changed

```dockerfile
# Slow: any source change invalidates the dependency install
FROM node:24-slim
WORKDIR /app
COPY . .
RUN npm ci --omit=dev
CMD ["node", "src/server.js"]
```

```dockerfile
# Fast: dependencies are reinstalled only when the manifests change
FROM node:24-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY src ./src
CMD ["node", "src/server.js"]
```

The second version copies the dependency manifests on their own first. Source code changes many times a day, but `package.json` rarely changes, so the expensive `npm ci` layer stays cached for almost every build.

Add a `.dockerignore` file to keep things the image doesn't need — `.git`, local `node_modules`, logs, documentation — out of the build context. It makes builds faster and stops irrelevant edits from invalidating `COPY` layers.

## Under the hood

**How the cache decides.** For most instructions the builder compares the instruction text with the cached layer. For `COPY` and `ADD` it also checks the files being copied; according to Docker's documentation, a change to a file's modification time alone does not invalidate the cache. For `RUN`, only the command string is compared — so `RUN apt-get update` stays cached even if the package repositories have changed since. That is why it is usually combined with the install in a single `RUN` instruction.

**Images, registries and pulls.** Layers are identified by a hash of their content. When you push an image, the registry only receives layers it doesn't already have; when a server pulls an image, it only downloads layers it lacks. Two images built on the same base image share those base layers on disk.

**Containers.** Starting a container stacks the image's read-only layers and adds a thin **writable container layer**. Everything the running container writes goes there; when the container is deleted, that layer is deleted with it and the image is unchanged. Many containers can run from one image at once, each with its own writable layer. Data that must survive — databases, uploads — belongs in a **volume**.

**Multi-stage builds.** A Dockerfile can use one stage with compilers and build tools, then copy only the finished artefacts into a small final stage. The final image contains none of the build tooling, which makes it smaller and gives attackers less to work with.

## In production

Teams pin base images to specific versions (or digests) so builds are reproducible, rebuild regularly to pick up security patches, and scan images for known vulnerabilities in CI. Images run as a non-root user where possible. In CI, where each build may start on a fresh machine, the local cache is often empty, so pipelines export and import build cache to keep the benefits of layer reuse.

## Common misconceptions

**"A container is a lightweight virtual machine."** Containers share the host's kernel and are isolated by kernel features; a virtual machine runs its own kernel on virtual hardware. The isolation boundaries are different.

**"Editing any file only rebuilds the layer that copies it."** It rebuilds that layer *and every layer after it*. Instruction order decides how much work that is.

**"Data written inside a container is saved in the image."** It goes to the container's writable layer and disappears when the container is removed. Use volumes for persistent data.

**"Deleting a file in a later layer makes the image smaller."** The file still exists in the earlier layer; the later layer only hides it. Avoid adding it in the first place, or use a multi-stage build.

## Failure modes and debugging

- **Every build reinstalls dependencies** — source is copied before the install step. Copy the manifests first.
- **Builds are slow to start** — a huge build context is being sent. Check `.dockerignore`.
- **Stale packages despite a rebuild** — a cached `RUN` instruction didn't rerun because its text didn't change. Combine update and install in one step, or rebuild without cache deliberately.
- **Huge images** — build tools and caches shipped in the final image. Use multi-stage builds and slim base images; `docker history <image>` shows which instruction added how much.
- **Data lost after a redeploy** — it was written to the container layer rather than a volume.

## Interview questions

<InterviewQuestion question="How does Docker's build cache work, and how do you structure a Dockerfile to make the most of it?">

Each instruction produces a layer whose cache key depends on its parent layer, the instruction and, for COPY or ADD, the copied files. If a matching layer exists it is reused; once one instruction misses, every later instruction rebuilds because its parent changed. So order instructions from least to most frequently changing: base image and system packages first, then dependency manifests and the dependency install, then application source last, and keep irrelevant files out with .dockerignore.

</InterviewQuestion>

<InterviewQuestion question="What is the difference between an image and a container?">

An image is an immutable, read-only stack of layers plus configuration. A container is a running instance of an image: the same read-only layers with a thin writable layer on top, plus its own process, network and resource settings. Many containers can run from one image, and removing a container deletes its writable layer but leaves the image untouched.

</InterviewQuestion>

<InterviewQuestion question="Why use a multi-stage build?">

To separate the environment needed to build software from the one needed to run it. Compilers, build tools and intermediate files stay in an earlier stage; only the finished artefacts are copied into a minimal final stage. The result is a smaller image that downloads faster and has a smaller attack surface.

</InterviewQuestion>

<InterviewQuestion question="Where should a containerised database store its data, and why?">

In a volume (or other persistent storage) mounted into the container, not in the container's writable layer. The writable layer is removed with the container and has write-performance overhead, while a volume persists independently of any container and can be backed up and reattached.

</InterviewQuestion>
